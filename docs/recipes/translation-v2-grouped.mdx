👤 Responsible: Project Leader

Use this GA workflow to translate Japanese Markdown and API Blueprint into Vietnamese while keeping document structure under deterministic control. V2 sends only cache misses to the model. Trusted scripts assemble the translated document and native-v2 cache, rewrite local document links, and prove the exact files that may be published.

Use [translation/v2/backfill](./translation-v2-backfill) for source documents that do not have output yet. If the output tree already belongs to `translation/v1`, follow the model-free [v1 to v2 migration guide](./translation-v2-migration). Translation v1 remains supported; migrate only when your repository is ready for the v2 cutover.

## What v2 creates

One Japanese document produces a translation/cache pair below `outputRoot`:

| Japanese source               | Reviewed translation                | Native-v2 cache                         |
| ----------------------------- | ----------------------------------- | --------------------------------------- |
| `docs/specs/account/login.md` | `docs_vn/specs/account/login.vi.md` | `docs_vn/specs/account/login.vi.json`   |
| `docs/specs/api/orders.apib`  | `docs_vn/specs/api/orders.vi.apib`  | `docs_vn/specs/api/orders.vi.apib.json` |

Same-stem sources such as `guide.md` and `guide.apib` are independent and produce four separate files. Each JSON file records schema version 2, the source path and commit, and the Japanese/Vietnamese wording pairs used for deterministic cache hits. Do not edit a cache to review prose. Edit the matching `.vi.md` or `.vi.apib`; the recipe synchronizes cache-only wording changes.

Compared with v1, the model does not write the final Markdown structure. It translates prepared wording segments only. The recipe preserves and checks headings, lists, tables, code, inline markup, link destinations, HTML destinations, and reference identifiers before publication.

## Prerequisites

- Keep Japanese Markdown and API Blueprint below one repository-relative folder, such as `docs/specs`.
- Choose a separate mirrored output folder, such as `docs_vn/specs`.
- Add a Markdown glossary with project terminology and translation rules.
- Use a sync branch and merge it into `syncBase` through a pull request.
- Protect `syncBase` and every branch in `gateBases` with the `cache-in-sync` check.
- Ask the BWV Workflows maintainers to confirm that your repository runs the translation v2 GA engine baseline and retained publication fencing.
- Ask the maintainers to make the official recipe repository available to your repository.
- Keep whitespace out of configured paths and document paths.

Run the recipe's v2 dry run against representative source documents before enabling it. An unsupported Markdown shape is refused before translation work begins.

## Add the workflow

Create `.bwv/workflows.yml` on the base branch:

```yaml title=".bwv/workflows.yml"
version: 1

workflows:
  - name: translate-specs-v2
    uses: BWV-Dev/bwv-workflows-recipes/translation/v2/grouped@translation/v2.0.0
    with:
      sourceRoot: docs/specs
      outputRoot: docs_vn/specs
      glossary: docs/glossary.md
      syncBase: main
      sourceBranch: docs-sync
      gateBases: [main, docs-sync]
      branchPrefix: bwv/translation
      model: haiku
      maxFilesPerGroup: 3
      maxRepairs: 1
```

The inline `@translation/v2.0.0` selects the recipe, skill, and trusted scripts together. In production, pin this immutable exact tag or, preferably, its full 40-character commit SHA. A branch or moving tag delegates trust to whoever can move that ref.

## Use the repository root as the source

V2 also accepts `sourceRoot: .` or `sourceRoot: ./` to translate from the repository root.

```yaml
with:
  sourceRoot: .
  outputRoot: docs_vn
  glossary: glossary.md
  exclude:
    - "archive/**"
    - "README.md"
```

At the repository root, the recipe selects `**/*.md` and `**/*.apib`. It always excludes the `outputRoot` tree, `.bwv/**`, `.github/**`, `.claude/**`, `.bwv-translation-v2/**`, and the glossary, then adds the caller's `exclude` list. For example, `screen/a.md` produces `docs_vn/screen/a.vi.md` and `docs_vn/screen/a.vi.json`; `screen/a.apib` separately produces `docs_vn/screen/a.vi.apib` and `docs_vn/screen/a.vi.apib.json`.

## API Blueprint ownership

V2 translates API names, ordinary prose, group and action display names, and descriptions that the Markdown and Blueprint parsers both identify as wording. It protects metadata, Blueprint keywords, URI templates, methods, status codes, media types, relation and identifier data, names and types, samples/defaults/enum values, named structures and references, code, assets, indentation, and non-prose Markdown syntax byte-for-byte.

Directive labels, titles, and attributes remain source-owned in this GA release. Descriptions after members under a parameter's `Members` or `Values` list also remain source-owned; named enum descriptions under Data Structures can be translated. Read the [frozen API Blueprint contract](https://github.com/BWV-Dev/bwv-workflows-recipes/blob/translation/v2.0.0/docs/v2-apib-contract.md) for the authoritative range rules and fixtures.

A prose line may be followed by physical lines that contain only `<br>`, `<br/>`, or `<br />`, with optional indentation. V2 accepts that shape, hides those protected lines from the model, and reproduces their exact spelling, indentation, EOL, position, and count. Adding, removing, respelling, or moving one fails the structural invariant.

The recipe owns four workflows:

- `draft` groups source files after a merged pull request from `sourceBranch` into `syncBase`, translates misses, and opens one draft translation pull request per source group.
- `sync-reviewed-cache` follows reviewer wording pushed below `branchPrefix` and updates only the affected `.vi.json` cache files.
- `cache-in-sync` is the pull request merge gate for translation output going into `gateBases`.
- `repair-base-v2-cache` is a deterministic safety net for translation output pushed directly to `syncBase`. When safe, it opens a draft repair pull request instead of committing to the base.

## Review wording and synchronize the cache

1. **Dev & Com:** Open the generated draft pull request.
2. **Dev & Com:** Edit Vietnamese wording directly in the `.vi.md` or `.vi.apib` files. Push the edit to the existing translation branch.
3. **Dev & Com:** Wait for `sync-reviewed-cache`. A valid wording edit produces a cache-only bot commit that changes the matching `.vi.json` or `.vi.apib.json` file.
4. **Dev & Com:** Wait for `cache-in-sync` to pass on the bot commit, then merge the pull request.

The first `cache-in-sync` run after a human wording edit can be red while the cache still contains the earlier wording. The deterministic cache commit should make it green.

Review wording only. Do not add, remove, reorder, or change the level of headings; do not change list, table, quote, directive, Blueprint, or block structure; and do not edit link targets, code, IDs, protected HTML attributes, protocol data, identifiers, assets, or standalone hard-break lines. Heading wording may change, but its structural position and level must remain aligned with the Japanese source.

Heading-structure mismatches are refused as `heading-structure`. The recipe also refuses a translated `\>` blockquote-content marker that the source does not have when the blockquote is the innermost owning container. Source-authored escapes remain valid, and list-item prose inside an alert remains wording.

When either check refuses a structural edit, restore the translation and make the structural change in the Japanese source instead:

> edit wording only; change structure in the Japanese source

`sync-reviewed-cache` blocks its cache commit when it cannot map the review edit safely. Protected edits fail closed and never produce a repair commit. `cache-in-sync` blocks the pull request from merging when an included native-v2 pair is missing, invalid, structurally different, or out of sync.

## Understand `pending`

A pair is `pending` when the Japanese source changed after the commit recorded by its current translation and cache. In plain words, the old translation is still waiting for its own grouped translation pull request.

Reviewer cache sync and base repair report and skip an untouched pending pair. This lets a reviewer finish another document while a sibling translation pull request is open. The merge gate also skips an untouched pending pair, but it fails if the current pull request changes that stale source, translation, or cache. Repair and backfill do not claim pending work; the pair belongs to its own grouped sync pull request.

## Recover from a red cache gate

First read the failing file and reason. Fix an ordinary wording/cache mismatch by pushing the `.vi.md` wording on a branch below `branchPrefix` and waiting for `sync-reviewed-cache`.

If deterministic base repair reports that the artifact cannot yet be reassembled, use this order:

1. **Dev & Com:** Restore trusted bytes in the `.vi.md` and commit them. Restore the expected `.vi.md` destination and anchor, serializer-owned HTML spelling, and required Markdown escaping. Remove only escapes that the serializer says are unnecessary.
2. **Dev & Com:** Let the next cache audit create the cache-only wording sync, review it, and merge it.
3. **Project Leader:** Run the failed artifact repair again. It can now reassemble from the synchronized cache without a model.

Do not hand-edit the cache to bypass the gate. One refused artifact makes the repository-wide repair transaction fail before it writes any file.

## Differences from v1 and migration

| Area                 | Translation v1                                                                        | Translation v2                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Model scope          | The translation skill writes the translation and cache, then a checker verifies them. | The model receives only prepared cache misses; trusted scripts assemble the final artifacts.           |
| Reviewer cache sync  | A cache-sync model updates reviewed wording.                                          | A deterministic script maps reviewed wording and updates the cache without a model.                    |
| Cache                | V1 cache format and checks.                                                           | A strict per-document schema-v2 cache with source metadata and complete structural ownership.          |
| Publication boundary | Required outputs and the v1 output checker.                                           | Structural proof, complete cache proof, sealed output digests, a publish allowlist, and clean scratch. |
| Adoption             | V1 remains supported.                                                                 | New trees can start directly; existing reviewed v1 trees use the model-free migration workflow.        |

Do not change only the `uses` line and point v2 at v1 caches. Follow the [migration runbook](./translation-v2-migration), which proves and converts the complete selected tree in one transaction.

## GA boundaries

- Per-document model processes in one group share a work directory. Read and edit permissions remain restricted per item, and every publishable output passes trusted structural gates.
- Container and leaf directive fence lines, labels, titles, and attributes remain source-owned structure.
- Visible identifiers, paths, versions, and dates can be ordinary wording. Review them carefully because the translation instructions retain them, but the gate does not reject every wording change to those visible values.
- V2 fails closed on unsupported source shapes, ambiguous reviewer edits, missing Git history, and damaged or ambiguous caches. Fix the source or restore the pair; do not bypass the gate.

## Common problems

### No translation starts after the sync pull request merges

Confirm that the pull request merged from `sourceBranch` into `syncBase`, changed an included `.md` or `.apib` file below `sourceRoot`, and did not match `exclude`.

### Reviewer cache sync creates no commit

If the check is green with zero drift, the cache already matches. If it is red, restore any structure or destination edit, then push wording-only changes again.

### The gate reports an unrelated stale base artifact

`cache-in-sync` is repository-wide for included native-v2 pairs. Merge the deterministic `repair-base-v2-cache` pull request, update the translation pull request from the clean base, and rerun the gate.
