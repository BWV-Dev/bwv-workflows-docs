👤 Responsible: Project Leader

Use this workflow recipe for a repository that synchronizes Japanese Markdown or API Blueprint documents through a dedicated branch and publishes reviewed Vietnamese translations to another branch. It groups files by their source pull request, creates one draft translation pull request per group, and checks that each translation and cache are complete before publication.

The recipe also keeps cache files aligned with wording that reviewers edit on a translation branch. Pull requests into the configured gate branches must pass the cache check.

After each document is translated, the recipe runs its deterministic `checkOutputs` toolkit script. A failed check can resume the same model session for a focused repair, then runs the check again. `maxRepairs` controls those model repair attempts; setting it to `0` keeps verification but disables model repair.

Translation v1.11.2, now included in the floating `translation/v1` tag, fixes cache checks for hard line breaks and indented continuation lines in paragraphs and block quotes. The publication gate now uses the same audit as `cache-in-sync`. A workflow that pins an exact version, such as `@translation/v1.11.1`, keeps running that version: change every translation `uses:` line to `@translation/v1.11.2` or `@translation/v1`, and merge the change into the branch whose `.bwv/workflows.yml` the run reads (the pull request's base branch, or the branch named in `/bwv run`). Then, if a pull request was blocked by `cache-in-sync` only because of this formatting, use **Retry** on that check; you do not need to regenerate the translation or cache.

## What users see on the pull request

Before the sync pull request merges, BWV Workflows adds a planned [translation tracker](../pull-requests/translation-tracker). After the merge, the same tracker shows each source group and its generated pull request.

Each generated pull request is a draft. Dev & Com review the Vietnamese document there, then follow [Running something again](../pull-requests/retry), [Recreating a closed pull request](../pull-requests/recreate), or [When a merge is skipped or needs mapping](../pull-requests/merge-skipped) when the tracker offers an action.

## Prerequisites

Prepare the target repository before adding the recipe:

- Keep the Japanese Markdown and API Blueprint documents below one repository-relative source folder, such as `docs/specs`.
- Choose a separate output folder that mirrors the source tree, such as `docs_vn/specs`.
- Add a Markdown glossary, such as `docs/glossary.md`, with project terminology and translation rules. Project rules in this file take priority over the recipe's generic rules.
- Use a sync branch, such as `docs-sync`, and merge it into the sync base, such as `main`, through a pull request.
- Protect the sync base and every gate branch so reviewed output cannot bypass the required checks.
- Ask the BWV Workflows maintainers to make the official recipe repository available to your repository.
- Keep spaces out of the configured paths and document paths. The recipe passes these paths as separate command arguments.

## Add the workflow

Create `.bwv/workflows.yml` on the base branch:

```yaml
version: 1

workflows:
  - name: translate-specs
    uses: BWV-Dev/bwv-workflows-recipes/translation/grouped@<full-sha-of-reviewed-tag>
    with:
      sourceRoot: docs/specs
      outputRoot: docs_vn/specs
      glossary: docs/glossary.md
      syncBase: main
      sourceBranch: docs-sync
      gateBases: [main, docs-sync]
      branchPrefix: bwv/translate
      model: sonnet
      maxFilesPerGroup: 3
      maxRepairs: 1
```

The recipe owns its triggers and uses its default toolkit when `toolkit` is omitted.

## Use the repository root as the source

`translation/v1` (from v1.10.0) also accepts `sourceRoot: .` or `sourceRoot: ./` to translate from the repository root.

```yaml
with:
  sourceRoot: .
  outputRoot: docs_vn
  glossary: glossary.md
  exclude:
    - "archive/**"
    - "README.md"
```

At the repository root, the recipe selects `.md` and `.apib` files recursively. It always excludes the `outputRoot` tree, `.bwv/**`, `.github/**`, `.claude/**`, `.bwv-translation-v2/**`, and the glossary, then adds the caller's `exclude` list. For example, `screen/a.md` produces `docs_vn/screen/a.vi.md` and `docs_vn/screen/a.vi.json`; the full repository-relative stem is preserved below `outputRoot`.

## API Blueprint (`.apib`)

Translation v1.11.1 supports API Blueprint and gives it a separate cache suffix. The floating `translation/v1` tag already includes it. The recipe selects `.apib` alongside `.md` below `sourceRoot`, including when `sourceRoot: .`. One source pull request that changes both formats produces one group, one tracker entry, and one output pull request.

For `sourceRoot: docs/specs` and `outputRoot: docs_vn/specs`, outputs map as follows:

| Source                       | Vietnamese translation             | Cache                                   |
| ---------------------------- | ---------------------------------- | --------------------------------------- |
| `docs/specs/api/orders.md`   | `docs_vn/specs/api/orders.vi.md`   | `docs_vn/specs/api/orders.vi.json`      |
| `docs/specs/api/orders.apib` | `docs_vn/specs/api/orders.vi.apib` | `docs_vn/specs/api/orders.vi.apib.json` |

Markdown paths are unchanged. Same-stem sources such as `a.md` and `a.apib` can be translated together because they produce four distinct files.

If v1.11.0 created an API Blueprint cache at `<outputRoot>/<rel>.vi.json`, v1.11.1 ignores it and writes `<outputRoot>/<rel>.vi.apib.json` on the next translation run. Delete the old cache if it is still present.

| Translate                                                                               | Keep verbatim                                                                                                                                                       |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prose; group and action names; resource names without `+ Model`; descriptions after `-` | Blueprint keywords and metadata; URIs, methods, status codes, and media types; parameter and attribute names, types, sample values, and enum values                 |
| Descriptive paragraphs, tables, and blockquotes                                         | Data Structures type names and references; resource names with `+ Model` and their references; all `Body`, `Headers`, and `Schema` code, including Japanese strings |

For example, the model may produce this small translation:

```apib title="api/orders.apib"
FORMAT: 1A
# 注文 API
# Group 注文
## 商品 [/items/{item_id}]
+ Model (application/json)
### 商品を取得する [GET]
商品を返します。
+ Response 200 (application/json)
    + Body
            {"name":"りんご"}
```

```apib title="docs_vn/api/orders.vi.apib"
FORMAT: 1A
# API đơn hàng
# Group Đơn hàng
## 商品 [/items/{item_id}]
+ Model (application/json)
### Lấy sản phẩm [GET]
Trả về sản phẩm.
+ Response 200 (application/json)
    + Body
            {"name":"りんご"}

<!-- translate-vi-meta
sourceCommit: 1111111111111111111111111111111111111111
sourcePath: api/orders.apib
translatedAt: 2026-11-05
-->
```

The metadata footer is always the last block of `.vi.apib`. Official Blueprint parsers may report a harmless “ignoring unrecognized block” warning for it. The recipe does not run a Blueprint parser or validator; it trusts the model to follow these preservation rules.

### Get the SHA of the latest tag

Replace `<tag>` with the latest release tag:

```bash
gh api repos/BWV-Dev/bwv-workflows-recipes/git/ref/tags/<tag> --jq '.object'
```

If the returned `type` is `commit`, use its `sha`. If it is `tag`, peel the annotated tag and use the commit SHA returned here:

```bash
gh api repos/BWV-Dev/bwv-workflows-recipes/git/tags/<tag-object-sha> --jq '.object.sha'
```

You can also inspect both the tag and its peeled commit with Git:

```bash
recipe_url=$(gh repo view BWV-Dev/bwv-workflows-recipes --json url --jq '.url')
git ls-remote --tags "$recipe_url" \
  "refs/tags/<tag>" "refs/tags/<tag>^{}"
```

Use the `^{}` row for an annotated tag. If that row is absent, use the tag row. A full SHA fixes the reviewed recipe version; `@translation/v1` can move without a change in your repository.

## Inputs explained

| Input                   | Meaning                                                                                                                                    | Example               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------- |
| `sourceRoot`            | Root of the Japanese `.md` and `.apib` source tree; `.` or `./` selects the repository root.                                               | `docs/specs`          |
| `outputRoot`            | Root folder for mirrored translations and their `.vi.json`/`.vi.apib.json` caches.                                                         | `docs_vn/specs`       |
| `glossary`              | Markdown file containing project terms and translation rules.                                                                              | `docs/glossary.md`    |
| `exclude`               | Source globs omitted from translation and cache checks. A supplied list replaces the default sentinel.                                     | `["docs/archive/**"]` |
| `syncBase`              | Base branch that receives the merged sync pull request and generated translation pull requests.                                            | `main`                |
| `sourceBranch`          | Head branch whose merged pull request into `syncBase` starts translation.                                                                  | `docs-sync`           |
| `gateBases`             | Pull request bases on which translation caches must remain synchronized.                                                                   | `[main, docs-sync]`   |
| `branchPrefix`          | Prefix for generated translation branches.                                                                                                 | `bwv/translate`       |
| `model`                 | Model used by the translation and cache-sync skills.                                                                                       | `sonnet`              |
| `maxFilesPerGroup`      | Maximum files in one group and maximum simultaneous translations for it.                                                                   | `3`                   |
| `timeoutMinutes`        | Per-document, per-attempt timeout for translation or cache sync. Defaults to `40`; maximum `90`.                                           | `40`                  |
| `maxTurns`              | Per-document, per-attempt Claude turn limit. Defaults to `40`.                                                                             | `40`                  |
| `maxBudgetUsd`          | Per-document, per-attempt runaway guard. Defaults to `6`.                                                                                  | `6`                   |
| `maxRepairs`            | Same-session model repairs after `checkOutputs` fails. Defaults to `1`; range `0`–`3`.                                                     | `1`                   |
| `allowedTools`          | Complete tool list for translation. Omit it to use the maintained default.                                                                 | Omitted               |
| `syncCacheAllowedTools` | Complete tool list for cache synchronization. Omit it to use the maintained default.                                                       | Omitted               |
| `toolkit`               | Complete replacement for the default translation, cache-sync, output-check, and drift-check tools. Omit it to use the maintained defaults. | Omitted               |

The default `checkOutputs` is a toolkit script and is valid in the translate step's `verify.shell`. A custom toolkit must keep the same `checkOutputs <source> <sourceRoot> <outputRoot>` contract: every existing cache entry must have the exact current structural owner required by the drift gate, and a leading HTML comment is invalid when the source has no comment at the same position. Enforce both rules so verification, model repair, publication, and `cache-in-sync` agree.

The released recipe sets `permissionDenials: warn` only on the translate step. A denied tool remains blocked and appears as a warning, while the per-document `checkOutputs` verifier and the final group-wide output check still prevent incomplete work from being published. A definitive item or verifier failure stops sibling processes and leaves queued files unstarted.

## Link rules

Translation v1 preserves each link's query string and fragment, then applies these destination rules:

- A relative link to Markdown or API Blueprint below `sourceRoot` points to the mirrored `.vi.md` or `.vi.apib` document below `outputRoot`, even when that translation does not exist yet. Anchors point to the translated heading.
- A relative image, PDF, CSV, or other non-Markdown destination continues to point to the original source-tree file. The path is recalculated from the translated document, including when the asset sits outside `sourceRoot`.
- Absolute URLs, root-absolute paths, anchor-only links, and `mailto:` links are left unchanged.

The output check compares the resolved relative destinations with the source. A source link that is already broken remains aimed at the same missing target and produces a warning; the recipe does not guess a replacement.

## Common problems

### No translation starts after a merge

Check that the pull request merged from `sourceBranch` into `syncBase` and changed a `.md` or `.apib` file below `sourceRoot`. The branch direction is significant.

### A group fails with missing outputs

Open the check run and inspect the named file. Every source must produce its mirrored `.vi.md` or `.vi.apib` translation and extension-specific cache. Fix the source, glossary, or custom toolkit, then follow [Running something again](../pull-requests/retry).

### The tracker says outputs are partly on the base branch

Do not retry immediately. Resolve the listed output files on the base branch first, then use the action offered by the [translation tracker](../pull-requests/translation-tracker).

### The cache check fails after a review edit

Check that the edit was pushed to a branch below `branchPrefix`. Read the cache-sync check result, fix any reported document structure or cache problem, and retry after the branch is corrected.

### A configured path is rejected

Use repository-relative paths without whitespace, `.` segments, or `..` segments. Confirm that the source folder and glossary exist on the base branch.
