## Step-by-Step Instructions

### 1. Choose a Claude task

👤 Responsible: Project Leader

A `claude` step must set exactly one task source:

| Field        | Use it for                                                        |
| ------------ | ----------------------------------------------------------------- |
| `prompt`     | Instructions written directly in the workflow.                    |
| `promptFile` | Instructions read from a repository file.                         |
| `skill`      | `.claude/skills/<name>/SKILL.md`. This is the strict skill form.  |
| `command`    | `.claude/commands/<name>.md`, or a skill used as a slash command. |

Only `skill` and `command` accept `args`. The named skill or command must
already exist on the base branch before a pull request can use it.

This workflow shows a direct prompt, a skill, and a command:

```yaml title=".bwv/workflows.yml"
version: 1
defaults:
  model: sonnet
  effort: high
  maxTurns: 30
  maxBudgetUsd: 6
  timeoutMinutes: 20
  permissionMode: acceptEdits
workflows:
  - name: maintain-specs
    on:
      pull_request:
        types: [opened, synchronize]
        base: [main]
        paths: ["docs/specs/**"]
    steps:
      - name: Summarize the change
        claude:
          prompt: Review the pull request diff and summarize the specification changes.
          allowedTools: [Read, Glob, "Bash(git diff:*)"]
      - name: Update the review file
        claude:
          skill: update-spec-review
          args: docs/specs
          allowedTools: [Read, Edit, Glob]
          disallowedTools:
            - "Edit(.bwv/**)"
            - "Edit(.claude/**)"
      - name: Check terminology
        claude:
          command: check-terminology
          args: docs/specs
          model: sonnet
```

Use these controls inside a `claude` block, except `timeoutMinutes`, which belongs on the step itself. Each can also be set in the root `defaults`:

| Field            | Behavior                                                                       |
| ---------------- | ------------------------------------------------------------------------------ |
| `model`          | Chooses the Claude model.                                                      |
| `effort`         | Passes `low`, `medium`, `high`, `xhigh`, or `max` to Claude CLI as `--effort`. |
| `maxTurns`       | Limits the number of agent turns.                                              |
| `maxBudgetUsd`   | Stops the step at a positive per-step budget guard.                            |
| `permissionMode` | Chooses `default`, `acceptEdits`, `dontAsk`, `plan`, or `bypassPermissions`.   |
| `timeoutMinutes` | Sets a positive whole-minute timeout.                                          |

A step value overrides the corresponding default. When omitted, the runtime
defaults are `sonnet`, 30 turns, `acceptEdits`, and 20 minutes. `effort` and
`maxBudgetUsd` have no runtime default and apply only when configured.

Choose the permission mode based on what should happen when Claude reaches for
a tool that is not in `allowedTools`:

| Mode          | What happens                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `acceptEdits` | Edits in the worktree are approved automatically. Use `disallowedTools` when you need to prevent a write.                           |
| `dontAsk`     | A tool outside the allowlist is denied immediately instead of waiting for approval. Claude sees the denial and can try another way. |

BWV Workflows records a denied attempt even when Claude completes the task by
another route. A Claude step therefore also accepts the step-level field
`permissionDenials: fail | warn`, which defaults to `fail`. Use `warn` only
when a later deterministic step verifies the required output:

```yaml title=".bwv/workflows.yml"
- name: Update the generated index
  permissionDenials: warn
  claude:
    prompt: Update docs/index.json from the Markdown files under docs/specs.
    permissionMode: dontAsk
    allowedTools: [Read, Glob, Grep, Write]
- name: Verify the generated index
  shell: ./.bwv/scripts/check-index.sh docs/index.json
```

With `warn`, a successful Claude CLI result may continue and the denied tools
remain visible as a code span in the step row's Notes cell. It does not turn a
failed CLI result into a success; any non-zero Claude CLI exit fails the step.

#### Restrict tools explicitly

Keep `allowedTools` narrow and list only the tools the task needs. Under the
default `permissionMode: acceptEdits`, narrowing `allowedTools` does not
prevent writes inside the worktree. Use `disallowedTools` for an actual write
restriction.

Scope file rules with `Edit(<glob>)`. Do not use `Write(<glob>)`; file write
permissions are evaluated through `Edit`. Never grant broad `Bash` in a step
that relies on a path deny. Grant only narrow, read-only shell rules such as
`Bash(git diff:*)`, because a general shell can reach the same files by another
route.

:::caution Keep permission denials failing by default
`permissionDenials: fail` prevents a run that produced no usable output from
appearing healthy. Choose `warn` only when a later deterministic gate checks
the output. Use `continueOnError: true` when later steps must handle an actual
step failure, not merely to hide denied tools.
:::

### 2. Run a shell command safely

👤 Responsible: Project Leader

A `shell` step runs `/bin/sh` in the checked-out worktree. Its trimmed stdout
becomes the step output. Set `outputJson: true` when stdout is one JSON value:

```yaml title=".bwv/workflows.yml"
version: 1
workflows:
  - name: inspect-spec
    on:
      pull_request:
        types: [opened, synchronize]
        base: [main]
        paths: ["docs/specs/**"]
    steps:
      - id: plan
        name: Select a specification
        shell: >-
          printf '%s\n'
          '{"file":"docs/specs/login.md"}'
        outputJson: true
      - name: Check the selected specification
        shell: >-
          ./.bwv/scripts/check-spec.sh
          "${{ steps.plan.output.file }}"
```

Pass runtime expressions as positional arguments to a script, as above. A
top-level expression or one inside double quotes is preserved as one argument
during the shell's first parse.

BWV Workflows refuses expressions in contexts that can change how the shell
parses the command: single quotes, arithmetic, command substitutions,
comments, expression-bearing heredocs, an expression after an unescaped
backslash, and unsupported parameter expansions. Move the value to a normal
positional argument instead.

Do not put runtime values into commands that parse their arguments again,
including `eval`, trap command strings, `sh -c` command strings, export
operands, or Bash arithmetic. Quoting protects the first parse only.

:::warning Review scripts from triggering branches
A direct `shell` step runs repository content from the checked-out commit.
Only people trusted to change automation should be able to push to a
triggering branch, because a change to a called script changes what the step
executes.
:::

### 3. Insert a step recipe

👤 Responsible: Project Leader

Use `uses` to insert the `steps` from a local recipe or an official shared
recipe:

```yaml title=".bwv/workflows.yml"
version: 1
workflows:
  - name: review-specs
    on:
      pull_request:
        types: [opened, synchronize]
        base: [main]
        paths: ["docs/specs/**"]
    steps:
      - id: review
        name: Review the changed specifications
        uses: ./.bwv/recipes/review-specs
        with:
          source: docs/specs
```

The recipe is expanded while configuration loads. No `uses` step remains at
runtime. A step-recipe caller may set `id`, `name`, `if`, and `with`; the
recipe's emitted steps own `forEach`, `fanout`, `maxParallel`,
`continueOnError`, and `timeoutMinutes`.

See [Recipes and toolkits](./recipes-and-toolkits) before calling an official
shared recipe.

### 4. Control failures, conditions, and timeouts

👤 Responsible: Project Leader

Use these fields on resolved `claude` and `shell` steps:

| Field               | Behavior                                                                         |
| ------------------- | -------------------------------------------------------------------------------- |
| `id`                | Makes the result available as `${{ steps.<id>.output }}`. IDs must be unique.    |
| `name`              | Labels the step in the check run and status comment.                             |
| `if`                | Runs the step only when the expression is truthy; otherwise it is skipped.       |
| `forEach`           | Requires an array and repeats the step for its items.                            |
| `fanout`            | Selects `process` or `subagent` execution for a repeated Claude step.            |
| `maxParallel`       | Limits parallel items; defaults to 3 and cannot exceed 20.                       |
| `continueOnError`   | Continues after this step fails. Defaults to `false`.                            |
| `permissionDenials` | On a Claude step, chooses `fail` or `warn` for denied tools. Defaults to `fail`. |
| `timeoutMinutes`    | Sets a positive whole-minute timeout for the step. Defaults to 20.               |

Without `continueOnError`, the workflow stops at the first failed step. With
it, the failed step and its output remain visible, and later steps may use the
recorded output. A non-zero shell exit, invalid JSON from `outputJson`, a
timeout, a non-zero Claude CLI exit, or a denied Claude tool under
`permissionDenials: fail` all count as failures.

`maxParallel` is a ceiling, not a promise that every slot starts immediately.
Runner capacity still decides how many processes can run at once. Engine
deployments that use memory requests with an aggregate limit can admit several
Claude processes while preserving each process's hard limit, so repeated steps
may run more items concurrently without a workflow change.

See [Passing data, forEach, and expressions](./passing-data) for repeated work
and expression contexts. Use the generated
[workflow configuration reference](/reference/workflows-yml) for the complete
field list.
