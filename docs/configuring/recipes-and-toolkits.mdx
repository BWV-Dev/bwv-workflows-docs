Reuse a local recipe or an approved remote recipe instead of copying its
steps. Pin every remote recipe to the exact commit you reviewed.

## Step-by-Step Instructions

### 1. Use a local recipe

👤 Responsible: Project Leader

Store project recipes under `.bwv/recipes/`. Reference a recipe from
`.bwv/workflows.yml` with a path that starts with `./.bwv/recipes/`:

```yaml title=".bwv/workflows.yml"
version: 1
workflows:
  - name: review-specs
    on:
      pull_request:
        types: [opened, synchronize]
        base: [main]
        paths: ["docs/specs/**"]
    steps:
      - name: Review the changed specifications
        uses: ./.bwv/recipes/review-specs.yml
        with:
          source: docs/specs
```

A workflow recipe is used from the `workflows` list. A step recipe is used
inside `steps`, as above. Recipes may use a sibling such as `./check.yml`, but
local recipe paths must stay inside `.bwv/recipes/`.

Commit the recipe before testing. BWV Workflows reads it from the same trusted
commit as `.bwv/workflows.yml`.

### 2. Pin a remote recipe

👤 Responsible: Project Leader

A remote recipe uses this form:

```text
<owner>/<repo>/<path>.yml@<ref>
```

For example, an official recipe starts with
`BWV-Dev/bwv-workflows-recipes/recipes/` and ends with a full 40-character
commit SHA. Open the [Recipe catalog](/recipes), choose a recipe, and copy its
complete `uses` example.

Ask the BWV Workflows maintainers to approve every remote source during
[repository onboarding](../getting-started/onboard-repository). A workflow
file cannot add a source to the approved list or grant the App access to it.

Get the commit behind the release tag before merging the configuration. First
inspect the tag object:

```bash
gh api repos/BWV-Dev/bwv-workflows-recipes/git/ref/tags/<tag> --jq '.object'
```

If its `type` is `commit`, use the returned `sha`. If its `type` is `tag`, peel
the annotated tag and use this result:

```bash
gh api repos/BWV-Dev/bwv-workflows-recipes/git/tags/<tag-object-sha> --jq '.object.sha'
```

Replace the recipe's `@<sha-of-latest-tag>` placeholder with that full SHA.
A full SHA keeps the reviewed recipe unchanged; a branch or movable tag can
select different content without a change in your repository.

### 3. Choose or replace a toolkit

👤 Responsible: Project Leader

A toolkit is a recipe input that maps the operations a recipe needs to skills,
commands, or scripts. During recipe expansion, it replaces `claude.run` and
`$[[ toolkit.<key> ]]` placeholders with those concrete entries.

This local step recipe declares a default toolkit:

```yaml title=".bwv/recipes/review-specs.yml"
apiVersion: 1
inputs:
  source:
    type: path
    required: true
  toolkit:
    type: toolkit
    contract: review checks the source; verify validates the result
    default:
      review: { skill: review-specs }
      verify: { script: .bwv/scripts/check-specs.sh }
steps:
  - name: Review specifications
    claude:
      run: $[[ toolkit.review ]]
      args: $[[ inputs.source ]]
      allowedTools: [Read, Edit, Glob]
  - name: Verify specifications
    shell: $[[ toolkit.verify ]] $[[ inputs.source ]]
```

Use the default when it meets the project. To override it, pass the complete
toolkit in `with`; an override replaces the whole set rather than merging one
key at a time. Every named skill, command, and script must exist at the trusted
commit.

Toolkit script paths run from the commit where their toolkit entry was
checked, not from the pull request's working tree. Inside a script, load a
helper relative to the script itself, for example
`. "$(dirname "$0")/lib.sh"`. A path relative to the current working directory
would read the checked-out branch instead.

Remote skill frontmatter may contain only `name`, `description`, `when_to_use`,
`argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`,
`version`, and `license`; any other key is refused so the step's own tool and
model settings remain authoritative. Remote toolkit commands are not
supported; use a project command override or the remote recipe's skill.

### 4. Read configuration errors

👤 Responsible: Project Leader

BWV Workflows expands recipes before a workflow runs. Missing inputs, unknown
`with` keys, missing toolkit files, invalid remote sources, and errors in
nested recipes are configuration errors.

For an open pull request or push, open the check named `bwv/config`. Its
**Invalid workflow config** summary identifies the recipe and the failing node.
On a pull request, fix `.bwv/workflows.yml` or the recipe on the base branch;
the pull request's own configuration does not govern that run.

After fixing and merging the configuration, start a new event or retry the
eligible workflow. See
[Reading the check run and status comment](../pull-requests/read-checks-status)
for the check layout.
