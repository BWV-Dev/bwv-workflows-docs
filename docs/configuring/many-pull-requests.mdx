👤 Responsible: Project Leader

Use `loop` when a push or manual request can create more work than one focused pull request should contain. Each pass plans one batch, runs every step, and publishes that batch before the next pass starts.

Suppose the fake repository `acme/web-app` updates many generated documentation files after a push. The workflow below uses a repository-owned planner to split that work into focused batches.

## `loop` or `forEach`?

They repeat different things and are often used together, as in the example below.

|           | `forEach`                                                  | `loop`                                                                |
| --------- | ---------------------------------------------------------- | --------------------------------------------------------------------- |
| Set on    | One step                                                   | The whole workflow                                                    |
| Repeats   | That step, once per item of an array                       | Every step, as a sequence of passes                                   |
| Publishes | Once, after all steps of the run                           | Once per pass: one pull request per batch, on its own branch          |
| Work list | An array known when the step starts, usually a step output | Recomputed from the Git tree by a plan step at the start of each pass |
| Stops     | After the last item                                        | When `while` is false, at `maxIterations`, or after two idle passes   |
| Triggers  | Any                                                        | `on.push` or `on.manual` only                                         |

Use `forEach` to process several independent items inside one run. Use `loop` when the whole job is too large for one pull request to review.

## Step-by-Step Instructions

### 1. Make the plan step describe one batch

👤 Responsible: Project Leader

Add a plan step before the work step. Make it inspect the current Git tree and return structured JSON with:

- The files in the next batch.
- A stable, Git-safe batch identifier.
- The amount of work left after that batch.

This example delegates planning to a repository script:

```yaml title=".bwv/workflows.yml"
version: 1
workflows:
  - name: update-doc-batches
    fetchDepth: 0
    on:
      push:
        branches: [main]
        paths: ["docs/specs/**"]
    loop:
      while: ${{ steps.plan.output.remaining > 0 }}
      maxIterations: 20
      closed: skip
    steps:
      - id: plan
        name: Plan the next batch
        shell: node scripts/plan-doc-batch.mjs
        outputJson: true
      - name: Update this batch
        forEach: ${{ steps.plan.output.files }}
        fanout: process
        maxParallel: 2
        claude:
          prompt: |
            Update the generated documentation for ${{ item }}.
            Do not change files owned by another batch.
          allowedTools: [Read, Write, Edit]
    onSuccess:
      createPullRequest:
        branch: "bwv/docs/${{ steps.plan.output.batchId }}"
        title: "docs: update ${{ steps.plan.output.batchId }}"
```

For example, the planner can return `{"batchId":"account-login","files":["docs/specs/account/login.md"],"remaining":3}`. Keep the script deterministic: the same Git state should produce the same plan.

`loop` requires an `on.push` or `on.manual` trigger. A pull request run has separate head and base branches, so it cannot safely cut later batches from one consistent branch.

### 2. Repeat while work remains

👤 Responsible: Project Leader

Set `loop.while` from the plan step's output. BWV Workflows evaluates it after each pass. A truthy result starts another pass in the same working tree; a false result finishes after the current batch is published.

Set `maxIterations` to a deliberate upper bound. It defaults to `20` and cannot exceed `100`. Every pass runs the workflow steps again.

A loop also stops after two consecutive passes publish nothing. This protects the run when a planner reports remaining work but the steps make no Git change. Fix the planner or the work step before starting another run.

### 3. Use a different branch for every batch

👤 Responsible: Project Leader

Make `onSuccess.createPullRequest.branch` vary with the planned batch. The example uses `${{ steps.plan.output.batchId }}`. A branch name that repeats during one run is refused because publishing the later batch would replace the earlier batch's pull request.

Do not derive the identifier only from a remaining count. A new push can change that count and make a later batch reuse an earlier name. Derive it from stable batch content, such as the first planned path plus a short hash when needed.

Each successful pass opens its own pull request. Reviewers can work on earlier batches while the running job plans later ones.

### 4. Resume from pending batches

👤 Responsible: Project Leader

Keep progress in Git. The planner must recompute completed and remaining work from repository files and history; BWV Workflows does not store a cursor or last-processed commit for the loop.

Before the first pass of every run, BWV Workflows loads the workflow's pending batch pull requests into its private work branch. Open batches are always loaded. Merged batches are already on the base branch. This lets a run that stopped halfway continue from its published batches instead of repeating them.

`loop.closed` controls closed, unmerged batches:

- Keep `closed: skip`, the default, to load them and treat their files as completed.
- Set `closed: redo` to leave them out and let the planner select their files again.

For a manually triggered loop with `closed: skip`, the hub lists closed batches and shows `/bwv recreate #N`. Comment that command in the same conversation to stop loading that closed batch and let the planner create a replacement. The command has no effect with `closed: redo` because those files are already eligible again.

<GitHubComment sample="manual-run-hub" author="BWV Workflows" />

A push that arrives during the run does not start a second job. When the current pass appears finished, the running job checks the branch again. If the branch moved, it merges the new base commits into its working branch and runs another bounded pass.

If the run reaches `maxIterations` while work remains, its published pull requests stay available. The next push or manual request starts a new run, loads pending batches, and recomputes the remaining work from Git.
